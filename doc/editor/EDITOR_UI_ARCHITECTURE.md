# ZEditor UI architecture (Unity-aligned)

ZEditor UI is built on ImGui docking. The structure mirrors Unity's editor shell without replacing the rendering stack.

## Layer map

| Unity | ZEngine | Role |
|-------|---------|------|
| `EditorApplication` | `Editor` / `EditorApplication` | Main loop, play mode, systems |
| `EditorWindow` | `EditorWindow` : `EditorView` | Dockable panel (`m_Title`, `OnGUI`, `m_Open`) |
| `EditorWindow.GetWindow<T>()` | `EditorUI::GetWindow<T>()` | Typed panel lookup |
| `Selection` | `EditorSelection` | Facade over `EditorSceneManager` |
| Dock / layouts | `DefaultLayout` + `EditorDockLayout` | Builtin presets + `.zlayout.json` |
| Window registration | `EditorWindowRegistry` | Builtin panel table (factory + metadata) |
| Play Mode views | `PlayModeView` | Shared base for `Scene` / `Game` viewports |

## Builtin panels

All dock titles are defined once in `Editor/EditorLayout/EditorLayoutWindowIds.h`. Panel constructors must use the same string (e.g. `EditorWindow(editor_ui, EditorLayoutWindowIds::kHierarchy)`).

**ZSlate-backed defaults (2026-05):** `Hierarchy`, `Project`, `Console`, `Inspector`, `Preview`, `Package Manager`, `Timeline`, `Blueprint`, `Animation`, `Material Editor`, and `UMG Designer` register ZSlate window classes at the canonical dock titles (`ZSlate*Window`). The legacy ImGui window classes (`HierarchyWindow` / `ProjectWindow` / `ConsoleWindow` / `InspectorWindow` / `GameWindow` / `SceneWindow` / `PackageManagerWindow` / `TimelineWindow` / `BlueprintWindow` / `AnimationWindow` / `MaterialEditorWindow` / `UMGDesignerWindow`) have been **removed** -- every panel is now `ZSlate*Window`. Reset layout (`Window > Layouts > Reset All Layouts`) or pick a builtin preset to pick up the new panels if an old `imgui.ini` still references orphaned `"ZSlate *"` tabs.

`ZSlateTimelineWindow` keeps its toolbar (play/pause/stop, loop and snap toggles, zoom, edit-mode cycle, time read-out, add-track) as a persistent ZSlate widget tree, while the timeline canvas (ruler + track lanes + clips + playhead) is painted directly through the active `UIRenderer` (`drawQuad`/`drawRect`/`drawText`) and hit-tested manually -- it is a custom canvas, not a widget subtree. Clip select + drag-move and ruler scrubbing are handled against `io.MousePos`; horizontal scroll is on the mouse wheel.

`ZSlateBlueprintWindow` follows the same toolbar + custom-canvas split: the "add node" / "delete selected" actions are a persistent ZSlate toolbar (the legacy ImGui right-click popup is gone), and the node graph (grid + nodes + square pins + bezier links) is painted through the active `UIRenderer` and hit-tested manually. Because the `UIRenderer` has no native line/curve primitive, bezier links are sampled into short axis-aligned quads (path-independent, so it renders identically on the native and ImGui-fallback backends). Node drag, output-pin -> input-pin link drag (with single-input-connection + type-match rules), link/node selection, middle-drag pan, and Delete are handled against `io.MousePos`.

`ZSlateAnimationWindow` reuses the same toolbar + custom-canvas split. The toolbar (play/pause/stop, speed +/-, loop / snap toggles, fps +/-, zoom +/-, time read-out) is a persistent ZSlate widget tree; the three working areas -- property list (left), curve editor (top-right) and timeline ruler (bottom-right) -- are custom canvases painted through the active `UIRenderer` and hit-tested manually. The property list is a click-to-expand channel tree whose row rects are recorded each paint for hit-testing; the curve editor draws a piecewise-linear curve over the selected scalar property (one of Position/Rotation/Scale X/Y/Z) using the same short-quad line sampling as Blueprint, with double-click-to-add, click-to-select, and time-only drag of keyframes; the timeline scrubs the playhead on click. Rotation channels are placeholder-zero (Quaternion -> Euler conversion is out of scope, matching the legacy window).

`ZSlateMaterialEditorWindow` is the third node-graph conversion and reuses Blueprint's toolbar + custom-canvas split. The "add node" palette (Const / Const3 / Tex2D / UV / Sample / Add / Mul / Lerp / Saturate) and "Delete Selected" live in a persistent ZSlate toolbar, replacing the legacy right-click category submenus; the full `MatNodeType` set (incl. Subtract/Divide/Clamp/Combine/Split/TextureCube/Constant2/Constant4) is still constructible via the data model. The graph is a custom canvas (grid + nodes + typed square pins + bezier links sampled into quads) painted through the active `UIRenderer` and hit-tested manually, with output->input link drag gated by exact pin-type match and single-input-connection rules. The right-hand panel paints a material-preview placeholder plus read-only properties for the selected node; the legacy in-node `DragFloat` constant editing is presented read-only here since the graph is a visual prototype not yet wired to a real material compile.

`ZSlateUMGDesignerWindow` is the first conversion of a *forms-heavy* panel (not a custom canvas): the entire chrome is a retained ZSlate widget tree. The toolbar (New / type-cycler / Add / Delete / asset-URL `SEditableTextBox` / Save / Load) is `SButton` + `SEditableTextBox`; the hierarchy is an `SScrollBox` of `SButton` rows (click-to-select, indent-by-depth, and drag-drop reparent driven by `SButton`'s native `OnDragDetected`/`CanAcceptDrop`/`OnDrop` hooks carrying a `UMGDragOp : FDragDropOperation` payload); the property panel is rebuilt on selection from each widget's `UMGPropertyBag` reflection surface, emitting `SDragFloat` (Float/Int/Vec2), `SCheckBox` (Bool), `SEditableTextBox` (String), and `SColorPicker` (Color) editors. The already-native live preview (`UWidget::TakeWidget()`) is painted into its own right-hand region. Chrome and preview share one `BatchedUIRenderer` pass but are routed through two independent `SlateInputRouter`s (each hit-tests its own cached geometry), so a continuous property drag never tears down the chrome -- the chrome rebuilds only on structural / selection / scale change (`m_UiDirty`), while a value edit sets preview-only dirty. Save / Load round-trip through `UMGAssetIO`.

**RTT -> native-backend image bridge (resolved 2026-05):** an external RHI render target can now be sampled by a ZSlate `SImage` through `UiGpuResources::AdoptExternalImageView` (allocates a UI-layout descriptor set pointing at a borrowed `RHIImageView`; on DX12 it relocates the SRV into the bindless heap via `EnsureShaderVisibleImageView`, which is the single shader-visible heap the overlay binds at draw time). The shader preview is the reference consumer: `DX12PreviewRenderer::DrawNative` renders the preview mesh into a persistent RTT and wraps it with `AdoptExternalImageView`. The earlier "preview never displays" bug was NOT a descriptor bug -- the offscreen draw was recorded on the **game thread's** frame command list and self-deferred whenever an (emulated) render pass was open (`IsInsideActiveRenderPass`), so the RTT was never populated. Fix: the offscreen draw now runs through `RenderSystem::RunSynchronizedGpuReadback` (flush in-flight frames -> marshal onto the RHI worker, the same primitive Scene-view picking uses) using a dedicated, fence-synchronized command list (`DX12RHI::ExecuteDedicatedUploadCommands`), so it is independent of frame render-pass state. The render is gated to run once per selection / shader-source-mtime change, so the per-call GPU flush is not paid every frame.

Viewports (`Game` / `Scene`) do NOT blit an RTT through `ImGui::Image`; they composite the 3D scene *under* a transparent (`ImGuiWindowFlags_NoBackground`) window by reporting their rect to `RenderSystem::UpdateViewport`, then draw editor overlays (grid / gizmo / camera preview) on top. A native ZSlate port therefore does not depend on the image-adoption bridge above -- it needs a ZSlate window that reports its rect and paints overlays, with input hit-tested manually.

- **`Game` viewport -- native ZSlate (done 2026-05):** `ZSlateGameWindow` (replaces the old `GameWindow`) is the reference native viewport. It paints only its informational text overlay (edit-mode camera-speed readout / play-mode cursor hint) through `BatchedUIRenderer` and then calls `PlayModeView::UpdateViewport`. It deliberately adds **no** `InvisibleButton` / input router: capturing the panel rect would steal mouse input from the game composited beneath it, so the overlay is purely presentational. The overlay tree is rebuild-gated (mode flip / camera-speed delta / UI-scale change) rather than rebuilt per frame.
- **`Scene` viewport -- native ZSlate (done 2026-05):** `ZSlateSceneWindow` (replaces the old `SceneWindow`). The interactive editor *chrome* now renders through ZSlate:
  - **Toolbar** (axis-mode toggles, 2D toggle, `Scene Camera`, `Display`) -> `SButton`s painted into the reserved menu-bar strip (`ImGuiWindow::MenuBarRect()`, kept via the `MenuBar` flag so the scene `WorkRect` stays below it) and routed with a dedicated `SlateInputRouter` hit-tested against that strip (no `InvisibleButton`, so the composited scene keeps mouse input).
  - **`Display` dropdown + right-click context menu** -> the existing reusable `ZSlatePopupMenu` (`Editor/Menu/ZSlatePopupMenu`). NOTE: contrary to an earlier revision of this doc, this popup-menu controller **already existed** (extracted from the menu bar; also used by the Hierarchy / Project / Console / Inspector windows). It was not new work for the Scene port.
  - **`Scene Camera` settings** -> a ZSlate floating panel hosted by a tiny inline controller (paint-on-top at `LayerId 1`, route via a dedicated router, outside-press dismiss). `ZSlatePopupMenu` only hosts `SMenu` rows, so a settings panel needs this separate inline host. Contents: FOV + camera-speed `SSlider`s (live value text), `SCheckBox`es for dynamic-clipping / occlusion / easing / acceleration, and `SEditableTextBox` numeric-entry rows for the near/far clip planes (-> `RenderCamera::m_Znear` / `m_Zfar`, far kept strictly > near, edits ignored while Dynamic Clipping is on -- matching the old ImGui `BeginDisabled` gate, with the boxes dimmed as the visual cue) and the camera speed-min/max range (-> `EditorInputManager::SetCameraSpeedRange`, which clamps both ends). The entry boxes parse with `strtof` and commit on Enter (rejected / stale text snaps back to the live value); the panel router forwards `ProcessChar` / `ProcessKey` only while it `HasKeyboardFocus()`, and the whole panel sets `chrome_capturing`, so typing into a box never drives camera nav (WASD also requires a mouse button held over the viewport).
  - Kept as direct **ImGui draw-list painting**: the editor grid and the camera-preview frame -- non-interactive overlays of 3D-projected lines / a framed rect, for which there is no ZSlate primitive (`UIRenderer` has no arbitrary `drawLine`). They pull in no ImGui *widgets*.
  - Kept as raw **input polling**: camera nav (orbit / pan / zoom / WASD) and click-to-pick read `ImGui::GetIO()` / glfw directly; these are input reads, not ImGui UI. Nav is suppressed while the cursor is over the toolbar or a popup / settings panel is open (`chrome_capturing`).
  - **Cross-window drag-drop -- restored via a global drag channel (done 2026-05):** the ZSlate drag op lives in the *source* window's `SlateInputRouter`, so a drag started in the Project / Hierarchy window is invisible to *this* window's router. To bridge that gap without de-singletonising the routers, `SlateDragDrop.h` adds a process-wide channel (`ZSlate::SetActiveDragOperation` / `GetActiveDragOperation`, inline + function-local-static => one instance across TUs). `SlateInputRouter` publishes its op when a gesture starts (in `ProcessMouse`'s drag-detect branch) and clears it in `EndDrag` / `Reset` (guarded to only clear when it owns the published op). Consumers must NOT assume the op is still published on the exact release frame -- the source router may clear it first, depending on window draw order -- so `ZSlateSceneWindow::HandleDragDropDrop` **caches the last non-null op** and fires the drop on **its own** left-release edge over the viewport `WorkRect`. The object under the cursor (via `EditorSceneManager::PickGObjectAtViewportUv`) becomes the drop parent. Payloads: `FAssetDragDropOp` (`PayloadType == "AssetPath"`, emitted by ZSlate Project `.zasset` rows) -> `EditorScenePlacement::RequestDrop` (deferred spawn, executed by `EditorUI`); the Hierarchy's `FDragDropOperation` (`PayloadType == "GObjectID"`) -> `EditorHierarchyReparent::Reparent` under the picked object (cycles refused by `Reparent`, self-drop guarded here). The payload discriminator strings live in `Editor/EditorDragDrop/EditorDragDrop.h` (`kZSlateAssetPayloadAssetPath` / `kZSlateAssetPayloadGObjectId`). The editor is single-threaded (game thread), so the channel needs no locking.

**Native GPU backend (P9: the only backend):** ZSlate panels render through `BatchedUIRenderer` + `ZSlateEditorOverlay`, unconditionally. The `r.ZSlate.NativeBackend` / `r.ZSlate.NativeMenuBar` toggles and the `SlateImGuiRenderer` per-window ImGui-draw-list fallback were retired; the native RHI backend is the sole renderer for the menu bar, dock, and every panel. Only `r.ZSlate.NativeSelfTest 1` (dev canary quad/label) survives. NOTE: `SlateImGuiTextMeasurer` (in `SlateImGuiRenderer.h`, historical name) is KEPT -- it measures over the ImGui font atlas the native renderer also draws from, and is the single source of truth for ZSlate text metrics. ImGui itself is still used structurally for panel hosting (`ImGui::Begin`) and input (`ImGui::GetIO` / mouse / keyboard).

### Editor shell chrome (`MenuController`)

The top strip drawn by `MenuController` (over the `Editor menu` host window) has two pieces, both now ZSlate-capable:

- **Main menu bar** (`File` / `Window` / `Edit` / ...) -> `ZSlateEditorMenuBar` (painted into the overlay's foreground draw list, with a modal ImGui capture window raised only while a dropdown is open so clicks don't fall through). P9: this is unconditional -- the ImGui `BeginMenuBar` fallback path was deleted.
- **Playback toolbar** (Play/Stop, Pause, Step) -- native ZSlate (done 2026-05). `DrawPlaybackToolbarNative` builds a 3-`SButton` `SHorizontalBox` whose content is a custom `SPlaybackIcon` leaf widget, painted through the overlay and routed by a dedicated `SlateInputRouter`. The tree is rebuild-gated on `(playing, paused, ui-scale)` so a press->release survives across frames. Disabled buttons (Pause/Step while stopped) flatten their hover/press colors and drop `OnClicked`; the toggled state (playing, or paused) uses the blue accent colors. Toolbar input is suppressed while a menu dropdown is open. P9: this is unconditional. The legacy ImGui `DrawPlaybackToolbarWindow` (InvisibleButton + draw-list icons) is now dead code (uncalled; pending a focused removal because its draw helpers share the `PlaybackToolbarIcon`/`Segment` enums with the native widget).

**New `UIRenderer` primitive -- `drawConvexPoly(points, count, color)`:** added to paint the toolbar's play/step **triangles** (a quad/outline can't express them). It is a virtual **no-op by default** (runtime UI backends never draw these icons), with the real implementation in `UiRenderBatch` (fan-triangulated into the shared vertex/index buffer; samples the white texel; clipped by the recorded command's clip rect via the overlay's GPU scissor). This is the convex-fill analogue of the still-absent `drawLine` (which is why Blueprint/Animation/Material links are quad-sampled, see above). (The former `SlateImGuiRenderer` `ImDrawList::AddConvexPolyFilled` implementation was deleted in P9.)

Registration lives in `Editor/EditorUI/EditorWindowRegistry.cpp` only. Adding a panel:

1. Add `kMyPanel` to `EditorLayoutWindowIds.h`.
2. Implement `MyPanelWindow` with matching title.
3. Append one row to `kBuiltinDescriptors` in `EditorWindowRegistry.cpp`.
4. Dock it in `DefaultLayout` via `EditorDockLayout::DockWindow(...)`.

`DefaultLayout` no longer includes concrete window headers.

## Selection

Prefer `EditorSelection::SelectGameObject` / `GetActiveGameObject` in new code instead of calling `GET_SYSTEM(EditorSceneManager)` directly. Existing panels can migrate incrementally.

## Inspector / Preview split

The Inspector and Preview panels are both native ZSlate (`ZSlateInspectorWindow` / `ZSlatePreviewWindow`); the `InspectorWindow/` directory now holds only UI-agnostic helper modules that both panels share (no ImGui drawer or panel class lives there any more).

| File | Role |
|------|------|
| `EditorWindow/ZSlateInspectorWindow/ZSlateInspectorWindow.{h,cpp}` | Inspector panel (GameObject + all asset inspectors, fully native ZSlate) |
| `EditorWindow/ZSlatePreviewWindow/ZSlatePreviewWindow.{h,cpp}` | Preview dock panel (native ZSlate; material/mesh/texture preview) |
| `InspectorWindow/InspectorAssetCommon.{h,cpp}` | Asset type resolution (incl. `IsTexture2DInspectorAssetType`), material load, project path helpers |
| `InspectorWindow/InspectorMaterialPreview.{h,cpp}` | Software material preview rasterizer -> ZSlate texture handle (consumed by `ZSlatePreviewWindow`) |
| `InspectorWindow/InspectorShaderInspector.{h,cpp}` | ShaderLab + ShaderRes inspector builder, shader variant UI, material shader binding helpers |
| `InspectorWindow/InspectorDataTableInspector.{h,cpp}` | DataTable `.zasset` inspector (CSV/XLSX edit, reimport, row introspection) |
