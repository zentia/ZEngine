# ZEngine 序列化库替换分析：JSON → YAML

## 一、当前实现概述

### 1.1 技术栈
- **当前库**: `json11` (轻量级 C++11 JSON 库)
- **核心文件**: `engine/source/runtime/core/meta/json.h`
- **序列化系统**: 基于反射的自动序列化 (`Serializer` 类)
- **代码生成**: 使用 Mustache 模板生成序列化代码

### 1.2 使用场景
- ✅ **资产文件序列化** (`AssetManager`)
  - 游戏对象配置 (`*.object.json`)
  - 关卡配置 (`*.level.json`)
  - 材质配置 (`*.material.json`)
  - 动画数据 (`*.animation_clip.json`)
  - 骨架数据 (`*.skeleton.json`)
- ✅ **运行时资产加载** (`Level::load`, `GameObject::load`)
- ✅ **编辑器资产保存** (`AssetManager::saveAsset`)

### 1.3 代码依赖
- `Serializer::write()` / `Serializer::read()` 返回/接受 `Json` 类型
- `AssetManager` 使用 `Json::parse()` 和 `Json::dump()`
- 代码生成模板 (`allSerializer.ipp.mustache`) 硬编码了 `Json` 类型

## 二、JSON vs YAML 对比分析

### 2.1 可读性对比

| 特性 | JSON | YAML |
|------|------|------|
| **可读性** | 中等（需要大量括号和引号） | ⭐⭐⭐ 优秀（缩进式，更接近自然语言） |
| **注释支持** | ❌ 不支持 | ✅ 支持 (`#` 注释) |
| **多行字符串** | 需要转义 | ✅ 原生支持 |
| **配置文件友好度** | 中等 | ⭐⭐⭐ 优秀 |

**示例对比**：

**JSON**:
```json
{
    "components": [
        {
            "$context": {
                "transform": {
                    "position": {
                        "x": 3,
                        "y": 3,
                        "z": 0
                    }
                }
            },
            "$typeName": "TransformComponent"
        }
    ]
}
```

**YAML**:
```yaml
components:
  - $context:
      transform:
        position:
          x: 3
          y: 3
          z: 0
    $typeName: TransformComponent
```

**结论**: YAML 在可读性上明显优于 JSON，特别是对于游戏资产配置文件。

### 2.2 性能对比

| 特性 | JSON | YAML |
|------|------|------|
| **解析速度** | ⭐⭐⭐ 快（语法简单） | ⭐⭐ 较慢（缩进解析复杂） |
| **序列化速度** | ⭐⭐⭐ 快 | ⭐⭐ 较慢 |
| **内存占用** | 较小 | 较大（需要维护缩进状态） |
| **文件大小** | 较小（紧凑） | 较大（需要缩进和换行） |

**性能数据**（参考）:
- JSON 解析通常比 YAML 快 **2-5倍**
- YAML 解析器通常比 JSON 解析器重 **3-10倍**

**结论**: JSON 在性能上有明显优势，特别是对于运行时资产加载。

### 2.3 兼容性和生态系统

| 特性 | JSON | YAML |
|------|------|------|
| **标准库支持** | 广泛（几乎所有语言） | 较少 |
| **工具支持** | ⭐⭐⭐ 优秀 | ⭐⭐ 中等 |
| **C++ 库选择** | 丰富（json11, nlohmann/json, rapidjson等） | 较少（yaml-cpp为主） |
| **Web 兼容性** | 原生支持 | 需要额外库 |
| **调试工具** | 丰富（浏览器、JSON查看器等） | 较少 |

**结论**: JSON 的生态系统更成熟，工具支持更完善。

### 2.4 语法特性对比

| 特性 | JSON | YAML |
|------|------|------|
| **类型系统** | 基础类型 | 更丰富的类型（日期、时间戳等） |
| **引用/锚点** | ❌ | ✅ 支持（`&anchor`, `*alias`） |
| **多文档** | ❌ | ✅ 支持（`---` 分隔） |
| **隐式类型转换** | ❌ 严格 | ⚠️ 有（可能导致意外行为） |

## 三、替换成本分析

### 3.1 代码修改范围

#### 必须修改的文件：
1. **核心序列化层**:
   - `engine/source/runtime/core/meta/json.h` - 替换 JSON 类型定义
   - `engine/source/runtime/core/meta/serializer/serializer.h` - 所有 `Json` 类型引用
   - `engine/source/runtime/core/meta/serializer/serializer.cpp` - 实现细节

2. **资产管理器**:
   - `engine/source/runtime/resource/asset_manager/asset_manager.h` - 解析/序列化逻辑

3. **代码生成模板**:
   - `engine/template/allSerializer.ipp.mustache` - 生成 YAML 相关代码
   - 可能需要修改反射代码生成器

4. **所有生成的序列化代码**:
   - `_generated/serializer/all_serializer.h` - 需要重新生成

#### 可能受影响的范围：
- 所有使用 `Json` 类型的代码
- 所有资产文件（需要转换格式）
- 编辑器工具（如果有）

### 3.2 第三方库选择

#### 推荐的 YAML C++ 库：

**yaml-cpp** (最流行)
- ✅ 成熟稳定，被广泛使用
- ✅ 支持 C++11+
- ✅ API 与 json11 类似
- ⚠️ 比 json11 重（需要链接库）
- ⚠️ 性能较 JSON 慢

```cpp
// 示例：yaml-cpp 使用
YAML::Node node = YAML::LoadFile("config.yaml");
int x = node["position"]["x"].as<int>();
```

**对比 json11**:
```cpp
// json11 使用
auto json = Json::parse(json_text, error);
int x = json["position"]["x"].int_value();
```

### 3.3 迁移工作量估算

| 任务 | 工作量 | 风险 |
|------|--------|------|
| 替换 JSON 库 | 1-2天 | 低 |
| 修改序列化接口 | 2-3天 | 中 |
| 更新代码生成模板 | 1-2天 | 中 |
| 转换所有资产文件 | 1-2天（自动化脚本） | 低 |
| 测试和调试 | 3-5天 | 中 |
| **总计** | **8-14天** | **中** |

## 四、适用性分析

### 4.1 YAML 适合的场景

✅ **推荐使用 YAML** 如果：
- 主要用途是**配置文件**（而非运行时数据）
- **可读性**是首要考虑（需要人工编辑）
- 需要**注释**功能
- 配置主要在**编辑时**使用，而非运行时频繁加载
- 团队更熟悉 YAML 语法

### 4.2 JSON 适合的场景（当前 ZEngine）

✅ **建议保持 JSON** 因为：
- **运行时资产加载** - 性能敏感
- **大量资产文件** - 需要快速解析
- **游戏引擎场景** - 性能优先于可读性
- **现有生态系统** - json11 轻量且稳定
- **代码已稳定** - 替换风险大于收益

### 4.3 混合方案建议

💡 **最佳实践**: 根据用途选择格式

```
配置文件（编辑时） → YAML
  - 引擎配置
  - 编辑器设置
  - 构建配置

运行时资产（运行时） → JSON
  - 游戏对象
  - 关卡数据
  - 动画数据
```

**实现方式**:
- 保持 `Serializer` 使用 JSON
- 添加 `ConfigLoader` 使用 YAML
- 两者互不干扰

## 五、风险评估

### 5.1 技术风险

| 风险 | 影响 | 概率 | 缓解措施 |
|------|------|------|----------|
| 性能下降 | 高 | 中 | 性能测试，必要时回退 |
| 兼容性问题 | 中 | 中 | 充分测试，保留 JSON 支持 |
| 资产文件迁移错误 | 中 | 低 | 自动化脚本 + 验证 |
| 代码生成器问题 | 高 | 中 | 充分测试生成代码 |

### 5.2 业务风险

- ⚠️ **开发时间成本**: 8-14 天工作量
- ⚠️ **测试成本**: 需要全面回归测试
- ⚠️ **维护成本**: 团队需要熟悉 YAML
- ⚠️ **向后兼容**: 需要处理旧 JSON 资产

## 六、结论与建议

### 6.1 总体评估

**替换 YAML 的合适度评分: ⭐⭐ (2/5)**

**理由**:
1. ❌ **性能劣势**: 运行时资产加载是性能敏感路径，YAML 解析慢 2-5 倍
2. ❌ **收益有限**: 主要收益是可读性，但游戏资产通常不需要频繁手动编辑
3. ❌ **成本较高**: 需要修改核心序列化系统，影响范围大
4. ✅ **当前方案合理**: JSON 在游戏引擎中是最常见的选择（Unreal, Unity 都使用 JSON/二进制）

### 6.2 推荐方案

#### 方案 A: **保持 JSON** ⭐⭐⭐⭐⭐（推荐）

**优点**:
- ✅ 零成本，无风险
- ✅ 性能最优
- ✅ 生态系统成熟
- ✅ 符合游戏引擎最佳实践

**缺点**:
- ⚠️ 可读性略差（但可通过格式化工具改善）

#### 方案 B: **混合方案** ⭐⭐⭐⭐

**实现**:
- 运行时资产 → JSON（保持现状）
- 编辑器配置 → YAML（新增）

**优点**:
- ✅ 各取所长
- ✅ 不影响现有系统
- ✅ 满足不同场景需求

**缺点**:
- ⚠️ 需要维护两套序列化系统
- ⚠️ 增加复杂度

#### 方案 C: **完全替换为 YAML** ⭐⭐

**适用场景**:
- 仅当可读性是绝对优先需求
- 且性能不是主要考虑因素
- 且团队愿意承担迁移成本

### 6.3 最终建议

**🚫 不建议替换为 YAML**

**替代改进方案**:

1. **改善 JSON 可读性**:
   - 使用 JSON 格式化工具（`jq`, Prettier）
   - 编辑器插件提供语法高亮和格式化
   - 自定义 JSON 序列化，改善缩进和格式

2. **如果必须改善可读性**:
   - 考虑方案 B（混合方案）
   - 仅在编辑器配置等非性能敏感场景使用 YAML

3. **性能优化**（如果当前 JSON 性能不足）:
   - 考虑二进制序列化（如 MessagePack）
   - 或使用更快的 JSON 库（如 rapidjson）
